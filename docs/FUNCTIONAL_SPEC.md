# Chronos（柯罗诺斯）功能设计 v0.2

> 状态：目标产品方案，更新：2026-11-05。本文定义完整功能，不代表功能均已实现。开发者 Elton，当前版本免费，双端按发布标准准备但不提交商店。iOS 默认进入独立的本机手账；设备使用能力尚未接入。Android 屏幕使用数据为可选预览模块，Web 屏幕使用图表仍是明确标记的样例。完成情况见 [实现状态](IMPLEMENTATION_STATUS.md) 与 [发布门槛](release/READINESS.md)。

## 1. 产品决定

Chronos 是一款帮助用户看清**自己的时间去向**、设定自选上限并获得适度提醒的应用。用户可以一键开始手动记录工作、学习、阅读等活动；系统允许时，另行展示手机应用使用时间。两种数据可能重叠，不能直接相加为“全天总时长”。图表负责呈现事实，文字负责指出可核查的发现。

| 项目 | 首版决定 |
| --- | --- |
| 数据范围 | 用户主动创建的手动活动记录，以及系统允许获取的应用/类别屏幕使用数据；不读取日历或推断睡眠。两种来源分开统计。 |
| 账号与同步 | 不需要账号；设置和允许保存的汇总数据默认留在本机。 |
| AI | 不接入首版；先用确定性规则产生可解释的事实洞察。 |
| 提醒 | 用户设置的目标提醒优先；通用洞察默认只在应用内展示。 |
| 控制权 | 用户可暂停目标、调整阈值与语气、关闭通用洞察；系统不私自更改目标。 |
| 跨平台 | 共用 Flutter 导航与设置，但使用数据的展示和监测遵守各平台原生边界。 |

**明确不做：**仅凭屏幕数据推断睡眠、工作效率或心理状态；惩罚性评价；强制屏蔽应用；后台持续上传应用使用明细；把 iOS 受保护报告数据导出给 Flutter 或云端 AI。

## 2. 用户任务与版本范围

### 2.1 核心用户任务

1. **我今天用了多久？** 进入应用先看到今日累计或明确的加载状态，并知道当前是设备数据、延迟数据还是演示。
2. **我正在做什么？** 打开首页即可点一次开始手动计时，不依赖手机使用权限；可暂停、继续、结束或稍后补记。
3. **时间在什么时候流走？** 找到手动活动与屏幕使用各自集中的时段，点选一小时或一天看明确数值。
4. **主要用在什么上？** 看手动活动类别以及应用或类别排行，并知道哪些项目比自己的正常水平多。
5. **最近是否在变化？** 对比近七天，区分今天的未完结数据与已结束的完整日期。
6. **我能控制什么？** 选定应用、设置合计上限、选择提醒语气并随时暂停。

### 2.2 优先级

| 优先级 | 范围 | 交付条件 |
| --- | --- | --- |
| P0：可用首版 | 首页一键手动计时、暂停/结束、补记与历史；屏幕使用授权与状态、今日累计、应用/类别明细、近七天每日累计、单个组合目标、一次超限提醒、设置与删除本地数据。 | 手动计时跨平台验证持久化和跨午夜；iOS 与 Android 真机均完成屏幕使用权限、读数和提醒验证，平台无法提供的图表有明确替代展示。 |
| P1：图表深化 | 24 小时分布、七天时段条、同星期基线对比、图表点选、事实洞察卡。 | 各平台可取得足够粒度的数据；对照系统报告校验读数。 |
| P2：个性化 | 多目标、工作日/周末规则、月历热度、可调节通用洞察频率、周回顾。 | 真实用户使用验证有价值，且数据保存范围和误报率可控。 |
| P3：可选 AI | 基于已验证指标的自然语言解释和问答。 | 用户主动开启；先通过隐私、平台能力与事实校验审查。 |

P0 的视觉应预留 P1 图表位置，但不能因缺少小时数据而生成估算条带。当前 Demo 已展示若干 P1 图表，它们是交互样例，不等于两个平台均已实现。

### 2.3 平台能力矩阵

| 体验 | iOS 实现方向 | Android 实现方向 | 发布前验证 |
| --- | --- | --- | --- |
| 手动计时 | 共用 Flutter 时间段模型与本机存储，不依赖 Family Controls。 | 共用 Flutter 时间段模型与本机存储，不依赖使用情况访问权限。 | 后台与重启恢复、暂停、跨午夜、时区变化、删除。 |
| 使用授权与应用选择 | Family Controls 授权、系统 `FamilyActivityPicker`；选择结果采用隐私 token。 | 用户在系统设置授予使用情况访问权限；本地列出可选择应用。 | 拒绝、撤销、重启后状态都正确。 |
| 今日/七天报告 | `DeviceActivityReport` 在 SwiftUI 报告扩展中呈现；Flutter 负责容器与路由。 | `UsageStatsManager` 查询允许的聚合统计。 | 与系统报告比对日期、时长、应用/类别口径。 |
| 小时轨迹 | 在报告扩展中尝试按时段构建，无法取得所需粒度时降级。 | 可评估使用事件构建近日期时段；事件历史有限，不承诺任意历史回填。 | 各时段之和、跨午夜、时区变化、缺失事件。 |
| 目标阈值 | `DeviceActivityEvent` 和 Monitor 扩展的阈值回调。 | 依据允许读取的使用统计进行后台检查。 | 累加口径、重复回调、后台延迟与重启恢复。 |
| 通知 | 单独申请系统通知权限。 | Android 13 及以上单独申请通知运行时权限。 | 关闭通知后仍保留目标，且不会声称已送达。 |

这张表是实现方向，不是已经验证的能力清单。Apple 的报告与监测在隐私保护的扩展中运行；Android 使用统计的查询范围与后台执行时间受系统约束。[Apple Device Activity](https://developer.apple.com/documentation/deviceactivity)、[Android UsageStatsManager](https://developer.android.com/reference/android/app/usage/UsageStatsManager)、[Android WorkManager](https://developer.android.com/develop/background-work/background-tasks/persistent/getting-started/define-work)。

## 3. 信息架构与首次使用

底部导航为 **今日 / 趋势 / 目标**。右上角进入 **设置**。应用首次打开先展示一页价值说明和一页隐私说明，不强制用户看完长教程。可以选择“查看演示”，但每个主页面都持续显示“演示数据”；演示模式不与设备数据混排。

### 3.1 手动计时与活动记录（TIM）

手动计时是无需系统授权的首页首要操作。首次打开、设备数据加载、拒绝或撤销屏幕使用权限时，用户仍能看到「开始计时」。点击后立刻创建本机“未分类”记录；首页的工作、学习、阅读快捷入口也可一键开始对应分类。分类和备注可稍后修改。底部导航保留计时入口，运行时显示“进行中”并打开控制面板。一次只允许一个活动计时器。

| 操作 | 行为 |
| --- | --- |
| 开始／暂停／继续／结束 | 每次开始或继续记录时间段；暂停区间不计入时长。切到后台或重启 App 后根据已保存的起始时间恢复，不要求持续后台执行。 |
| 分类与备注 | 分类为未分类、工作、学习、阅读、运动、休息、生活、社交、其他；备注可选。运行中可改分类与备注。 |
| 补记与修改 | 选择起止日期时间，拒绝未来结束、负时长及与另一条手动记录重叠的区间。含暂停的记录不直接改写为连续区间；若要调整时间，删除后补记。 |
| 今日和历史 | 今日显示手动记录总时长、24 小时位置与最近记录；“全部”按日期浏览并编辑。跨午夜记录按本地日界拆分到两天。近七天显示独立的手动记录趋势。 |
| 删除 | 单条记录需要确认；设置中的删除本地数据同时清除全部手动记录。 |

**数据可靠性与可携带性（0.2）：**原生端使用 SQLite 事务，升级时先校验再迁移旧记录，成功后清理旧偏好；写入失败保留上次成功状态。手账设置可单独删除全部手动记录并明确保留设备目标与系统历史。导出 JSON 只含手动记录，运行中计时转为截至导出时刻的已结束快照，不影响本机继续计时。恢复先预览记录数量、再确认合并；相同记录跳过，同标识内容不同或区间重叠则整次拒绝，不覆盖本机。恢复前须结束正在进行的计时。CSV 仅供表格查看，不能恢复。备份上限 8 MB、50,000 条，文件不加密，用户通过系统选择器决定保存位置。Android 可记住“只用时间手账”，iOS 默认手账，不依赖使用时间权限。

手动记录是用户输入，不代表系统确认活动确实发生。它与手机使用时间可能重叠，例如“学习 2 小时”期间用手机 30 分钟。两个图表分别标注来源，不展示简单相加的全天总数。Web 演示中的手动计时是浏览器本机真实记录，固定屏幕使用样例仍持续标注为演示数据。

### 3.2 首次使用流程（ONB）

| 步骤 | 画面和操作 | 结果 |
| --- | --- | --- |
| ONB-01 价值说明 | 三张可扫读的预览卡：今日去向、七天变化、自己设定的提醒；按钮“连接设备使用时间”和“先看演示”。 | 用户知道应用需要什么数据、能得到什么价值。 |
| ONB-02 使用权限 | 先说明仅读本机允许的屏幕使用数据，再进入对应平台的系统授权或设置页。 | 授权成功进入真实数据加载；拒绝则进入说明页，可重试或看演示。 |
| ONB-03 通知权限 | 仅在用户创建并启用首个目标时请求，先展示提醒示例。 | 拒绝通知不阻止查看图表；目标页显示“目标已保存，系统通知未开启”。 |
| ONB-04 数据确认 | 首次成功读取后显示“最近读取 HH:mm”和数据来源；若系统提供可靠的数据截止时间，再显示“数据截至 HH:mm”。若暂时无记录，展示等待说明。 | 不把未读取到的数据当作 0 分钟，也不把读取时间冒充为数据截止时间。 |

iOS 使用 Family Controls 的个人授权与系统应用选择器；应用和扩展发布前需要 Family Controls distribution entitlement。Android 使用系统“使用情况访问权限”；Android 13 及以上另有通知运行时权限。授权状态可能在系统设置中被撤销，应用每次回到前台都要重新检查。[Apple 授权](https://developer.apple.com/documentation/familycontrols/authorizationcenter)、[Apple entitlement](https://developer.apple.com/documentation/familycontrols/requesting-the-family-controls-entitlement)、[Android 使用统计](https://developer.android.com/reference/android/app/usage/UsageStatsManager)、[Android 通知权限](https://developer.android.com/develop/ui/compose/notifications/notification-permission)。

## 4. 今日页（TOD）

首页从上到下只回答四个问题。卡片标题采用“结论 + 证据”，避免“你正在变好”之类无法从数据直接证明的文案。

| 模块 | 内容与交互 | 边界及替代 |
| --- | --- | --- |
| TOD-01 今日摘要 | 最大数字是今日累计时长；旁边标明最近读取时间，可靠的数据截止时间可另行显示。比较标签写“比上周同星期同一时刻多/少 X 分钟”；点标签查看比较口径。 | 没有可比日时隐藏差值，不写“持平”。今天不与上周完整一天直接比较。 |
| TOD-02 24 小时轨迹 | X 轴为本地时间 00–24 时，一柱为一小时的使用分钟数；点柱显示时段和准确值。标注使用最集中的连续三小时及其总量。 | 仅在系统提供足够时段数据时出现；否则显示“今日时段详情暂不可用”和应用排行。0 使用与缺失数据使用不同样式。 |
| TOD-03 去向明细 | 按时长排序列出应用或类别：名称、时长、占可比总量的比例。进入明细可查看近七天走势。 | iOS 的应用标识与受保护报告在原生扩展内展示；Flutter 不要求获取匿名选择器的真实应用名。 |
| TOD-04 基线对比 | 每项一条横向条：填充为今天，竖线为过去三个相同星期几的可比时刻平均；文字明确写“多/少 X 分钟”。点开解释样本天数。 | 至少有 2 个有效样本才显示基线；不足时只显示当前值。类别口径变更时暂停历史比较。 |
| TOD-05 目标摘要 | 当前目标名称、已用/上限、提醒开关状态、进入编辑按钮。 | 无目标时显示“为想减少的应用设一个上限”；无使用权限时可草拟目标，但不可显示进度或承诺提醒。 |

**首页排序：**今日摘要优先；若时段轨迹可用，它紧随摘要出现，否则由应用排行接替。类别明细与目标继续向下滚动。不要同时堆叠多个环形图。数字和单位始终可读；颜色只辅助区分，不能独自传达正负变化。

## 5. 趋势页（TRD）

默认显示**截至今天的最近七个本地日历日**，每一天都带星期和日期；今天标“进行中”。允许点选一天，选中状态跨今日/趋势切换保留。

| 模块 | 内容与交互 | 解释规则 |
| --- | --- | --- |
| TRD-01 七天时段条 | 一行一天，24 格或等价时段图；明暗表示该小时使用量，右侧显示日累计。点某行更新下方详情。 | 图例写“颜色越亮，使用越久”；没有时段数据时改为七天日累计柱形图。 |
| TRD-02 每日累计图 | 七柱展示各日当前可得的累计时长；选中完整日期时显示与有效完整日均值的差。 | 今天只显示“截至现在”时长或与同一时刻基线的差，不进入完整日最高/最低排名；完整日样本少于 2 天时不下结论。 |
| TRD-03 选中日详情 | 该日最集中的连续三小时、前几位应用或类别、与自身基线的差异；每项都可返回原图定位。 | 仅显示平台实际支持的项目；不把类别总和自动写成设备总屏幕时长。 |
| TRD-04 周发现 | 最多一到两条事实发现，如“周三 18–21 时最集中”或“工作日均值比周末高 40 分钟”。可点开计算依据。 | 只在样本充足、差异超过噪声阈值时显示；不要自动给行为下价值判断。 |

P2 月历仅表示**屏幕使用强度**，每格可点出日期与数值，不使用“工作时长”或“睡眠时间”标签。Android 的事件明细可能只保留数天，因此长时间的时段图依赖从用户授权后在本地积累的合法汇总数据，不能承诺回填任意历史日期。[Android UsageStatsManager](https://developer.android.com/reference/android/app/usage/UsageStatsManager)。

## 6. 目标与提醒（GOL / ALR）

### 6.1 创建与编辑目标

P0 只允许一个**每日组合上限**：用户选择一个或多个应用，设置总时长（15 分钟至 12 小时，15 分钟步进），默认每天生效。目标编辑页包含：名称、应用选择、时长、启用状态、提醒语气、通知预览、保存。iOS 打开系统 `FamilyActivityPicker`；Android 在本地应用列表中选择。保存前显示“这些应用合计达到 X 小时后提醒一次”。

同一应用只计入一次；跨午夜以设备当前本地日历日重置。更换时区或夏令时当天按实际本地日期处理，不假设每天都有 24 个经过小时。编辑上限后，下一次检查按新规则计算；如果当日已超过新上限，是否立即补提醒须通过真机验证，首版倾向于在下一次可用检查时提醒且写明“检查到已超过”，不补发旧日期提醒。

### 6.2 规则与通知

| 规则 | 首版行为 |
| --- | --- |
| ALR-01 触发 | 选中应用**合计**达到用户设置的阈值；一个目标每天最多通知一次。持续超限不会每隔几分钟再推送。 |
| ALR-02 内容 | 必须说明目标名称、阈值与事实，例如“你设置的短视频应用已达到今天 2 小时上限”。不宣称已经封锁应用。 |
| ALR-03 语气 | 温和、直接、严格三档。严格可以明确要求停下，但不辱骂、不羞辱、不诊断成瘾。预览与真实通知使用同一套经审核模板。 |
| ALR-04 控制 | 用户可关闭系统通知、暂停目标至明天或手动恢复、编辑阈值。暂停状态在目标卡明显可见。通知点击后打开对应目标页。 |
| ALR-05 失败 | 权限撤销、通知被拒、监测不可用时，目标状态明确显示“暂不能提醒”及修复入口；保留目标设置。 |
| ALR-06 时间 | iOS 借助 Device Activity 的阈值回调；Android 后台检查可能延迟。文案统一为“达到后提醒，送达时间可能受系统影响”，不承诺准点。 |

iOS 的 `DeviceActivityEvent` 与 `DeviceActivityMonitor` 支持所选应用的阈值和回调。Android 的周期任务受系统调度影响；WorkManager 周期任务至少 15 分钟，而且执行时间并不精确。系统通知权限由用户单独授予。[Apple Device Activity](https://developer.apple.com/documentation/deviceactivity)、[Apple 阈值回调](https://developer.apple.com/documentation/deviceactivity/deviceactivitymonitor)、[Android WorkManager](https://developer.android.com/develop/background-work/background-tasks/persistent/getting-started/define-work)、[Apple 通知权限](https://developer.apple.com/documentation/UserNotifications/asking-permission-to-use-notifications)、[Android 通知权限](https://developer.android.com/develop/ui/compose/notifications/notification-permission)。

**同一事实的语气示例：**温和：“你设置的短视频目标今天达到 2 小时了，休息一下吗？”；直接：“短视频目标已达到今天的 2 小时上限。”；严格：“你已达到自己设置的 2 小时上限。现在暂停刷屏，回到原定安排。”通知使用用户给目标起的名称，不要求 iOS 提供匿名选择器中的应用真实名称。

### 6.3 通用洞察与“少提示”

P1 在应用内展示通用事实洞察，例如“最近 7 个有效日中，有 5 天 22:00 后仍有屏幕使用”。不把它改写成“你睡得太少”。默认**不推送**通用洞察。用户点“少提示这类”后，该洞察类型 30 天不主动出现，之后可在设置中恢复；用户也可选择“只看图表”。这项偏好不影响用户自己设定的目标提醒。

系统从不因“正常习惯”反馈而暗中改写目标或个人基线。若未来接入睡眠数据，必须另行取得明确授权并重新设计睡眠相关文案与风险评估。

**典型流程：**用户选择抖音和小红书并设合计 2 小时，语气选“严格”；当天达到上限后收到一次目标通知，点开可看该目标状态。之后他对一条“夜间使用较多”的通用洞察点“少提示这类”，只会减少夜间使用洞察的出现次数；2 小时目标及其严格提醒保持原样。若要停掉目标提醒，须在目标页明确暂停或关闭。

## 7. 事实洞察与可选 AI（INS）

### 7.1 不依赖 AI 的洞察引擎（P1）

流程为 **可用数据 → 指标计算 → 候选事实 → 质量门槛 → 展示**。每张卡保存指标名、时间范围、比较口径、样本数、源图表定位和可供解释的一句话。候选规则：

1. 与自己过去三个相同星期几的可比时刻相比，变化达到至少 30 分钟且超过基线 20%。
2. 最近七个完整日中，某应用类别的日均变化达到至少 30 分钟。
3. 一天内最集中的连续三小时占当日已知使用时长的至少 35%。

这些是**初始产品阈值，待真实数据验证**，不是健康标准。数据不足、跨平台定义不一致或来源变更时不生成洞察。展示按“与用户目标相关、变化幅度、近期是否重复”排序，每日最多 2 条；同类型连续重复只保留更新后的最新卡。每条卡都能点进证据图表。

### 7.2 AI 的位置（P3）

AI 只负责把**已验证的事实**表述得更清楚，并可按用户选择的语气提出温和建议；阈值判定、通知触发和数值计算仍由确定性逻辑完成。AI 输出必须带来源时间范围和可核查数字；无法核查就不展示。它不能诊断睡眠、成瘾或生产力，也不能改变目标。

开启 AI 需要单独选择参与方式和数据范围。优先评估本地处理；任何云端处理都要另有明确的产品决定与单独同意。iOS 受保护的 Device Activity Report 数据不得为 AI 而越过扩展边界。若这条边界使跨平台 AI 无法一致实现，就只保留非 AI 洞察，不以虚构摘要补齐。

## 8. 指标口径与数据质量

| 指标 | 定义 | 展示约束 |
| --- | --- | --- |
| 今日累计 | 平台报告的当前本地日历日应用前台使用时长。 | 标注最近读取时间；数据截止时间仅在可靠时标注。不要把各应用相加后直接宣称为独立的“亮屏总时长”，除非平台口径已核对。 |
| 小时使用 | 一小时内符合平台定义的使用分钟数。 | 仅在可获得足够粒度时绘制；每小时理论上不超过 60 分钟，异常值不展示为正常柱。 |
| 日累计 | 指定本地日历日的可比使用总量。 | 今天标“进行中”；完整日可参与排名。 |
| 类别占比 | 平台提供或产品明确定义的类别时长占比。 | 类别映射变化时重算并标注；类别之和若与总量不一致，展示“未分类/不可归类”。 |
| 基线 | 过去三个相同星期几的日期在同一时刻的均值；完整日期则对完整日期。 | 至少 2 个有效样本；展示样本数与缺失原因。 |
| 目标使用 | 用户选定应用在当前目标周期内的合计使用。 | 已用/上限只在该平台可读取相同口径时展示；不可读时显示监测状态，不伪造进度。 |

统一数据状态为：`notRequested`、`loading`、`ready`、`partial`、`empty`、`permissionDenied`、`permissionRevoked`、`unsupported`、`error`、`demo`。`empty` 表示已成功读取但没有记录；`ready` 且值为 0 才能写“0 分钟”；`partial` 明示缺失的时段或应用。图表和洞察都要收到数据状态后再决定展示，而不是把 `null` 当 0。

## 9. 设置、隐私与无障碍（SET）

P0 设置页包含：使用权限状态、通知权限状态、当前数据模式、提醒语气、数据说明、删除本地数据。外观可选暮光星图、晨雾纸感、日落脉冲或跟随系统；系统浅色映射晨雾纸感，深色映射暮光星图。切换即时生效、在本机保存，不改变图表选中项、目标或使用数据。P1 增加通用洞察开关；P2 视用户需要增加应用内静默时段。在静默时段功能上线前，尊重操作系统的勿扰设置，不承诺应用内排程。删除本地数据要说明会清除何种汇总与偏好，以及是否保留目标；首版默认一并删除，需用户确认。撤销系统权限不等于删除已保存的本地设置。

可访问性要求：重要数字有文本标签；图表点选目标至少符合平台可触达尺寸；支持文字放大、屏幕朗读、减少动态效果；颜色之外还有文字、形状或图例；每张图提供可读的数值列表或语义摘要。小屏（如 390 像素）不横向溢出。数据图刷新不打断当前选择和滚动位置。

隐私说明必须用用户可理解的话回答：读了什么、存在何处、通知如何触发、是否发送给第三方、如何撤销权限和删除数据。首版不接入第三方行为分析 SDK。

## 10. 关键状态与异常流程

| 场景 | 用户看到什么 | 可执行操作 |
| --- | --- | --- |
| 首次未授权 | 带示例图的授权说明，不显示真实数值。 | 申请权限、查看演示。 |
| 拒绝或撤销权限 | 明确写“无法读取设备使用时间”，目标监测状态标为不可用。 | 打开系统设置、重试、继续看演示。 |
| 已授权但暂无记录 | “还没有可展示的使用记录”，不显示 0 分钟洞察。 | 稍后刷新、查看数据说明。 |
| 数据只覆盖部分日期 | 已知数值正常显示，缺失日期留空且标“无数据”。 | 查看原因；不足样本的比较隐藏。 |
| 通知未授权 | 目标可保存，但不显示“提醒已开启”。 | 开启系统通知、仅在应用内查看目标。 |
| 后台检查延迟 | 在目标页标“上次检查 HH:mm”；超过阈值后不倒填虚假的准确触发时间。 | 手动刷新、查看系统限制说明。 |
| 系统或扩展故障 | 清晰的暂时不可用状态，保留设置，不自动切到演示数值。 | 重试、打开帮助。 |

## 11. 验收场景

1. 新用户拒绝使用权限后，所有真实数据位均为空状态；点击“查看演示”后每页有明显演示标记。
2. 当前时间为 15:00 时，今日与上周同日的对比都截止 15:00；当天尚未结束，不参与完整日最高/最低排名。
3. 最近七天有两个缺失日时，趋势图留空并标注；洞察引擎只用有效样本，达不到门槛就不输出比较。
4. 用户选择两个应用并设置每日 2 小时目标；两应用合计达到阈值后当天最多通知一次，第二天重置。禁用通知后目标仍保存但状态正确。
5. 用户将目标提醒语气设为“严格”，通知只能使用经审核的严格模板；点击“少提示这类”只影响通用洞察，不改变目标提醒。
6. 权限在系统设置被撤销后，返回应用立即显示撤销状态；不保留过期图表当作最新数据。
7. 390 像素手机和放大文字下，所有主页面可滚动、图表有数值替代、无横向截断。
8. iOS 与 Android 真机分别对照系统报告验证日累计、应用/类别口径、阈值触发和通知权限；未通过的平台能力不进入发布承诺。
9. 打开 App 后点击首页「开始计时」一次就开始本机记录，不要求先授权屏幕使用数据；暂停时长不计入统计，关闭并重开 App 后可恢复未结束的记录。
10. 补记跨午夜的 30 分钟记录时，两天各计入对应时段；手动记录与屏幕使用时间不相加。

## 12. 开发顺序与决策门槛

1. **能力验证（先做）：**在真机上确认 iOS Family Controls 授权、Report 扩展可展示的粒度、应用选择、阈值回调、分发 entitlement；确认 Android 使用权限、日统计、事件保留期、后台检查与通知。产出设备/系统版本/结果表。
2. **真实数据只读版：**接入数据状态、今日累计、近七天每日累计和应用/类别明细；保留现有演示入口但严格隔离。先核对平台数值，再增加解释文案。
3. **目标闭环：**应用选择、合计上限、权限处理、一次提醒、暂停与编辑；覆盖撤销权限和后台延迟。
4. **图表深化：**在已验证的平台能力内加入时段条与基线对比。若 iOS 只能在原生报告扩展中实现，就在该扩展中做等价视觉，并让 Flutter 容器展示明确的导航和状态。
5. **事实洞察：**以可追溯指标实现卡片和“少提示”；根据真实误报反馈调整阈值。
6. **AI 评估：**等非 AI 价值和隐私边界得到验证后，再决定是否做可选的语言解释。

**尚需产品决定：**是否把多目标提前到 P0、是否提供工作日/周末不同阈值、是否允许静默时段延后目标通知、是否做月历，以及是否增加独立的“应用详情页”。这些不会阻塞前两阶段的能力验证和只读版开发。
