## Android validation

- A debug APK built and installed on an Android 13 physical device. The user granted usage access through system settings; Chronos then displayed real app labels, today's total and trend pages.
- The device returned some historical app durations close to 24 hours. The reader now checks app foreground totals against Android screen-interactive event totals; inconsistent dates display as unavailable and do not affect insights. This is a conservative quality gate, not a substitute for comparing figures with the device's system Screen Time report.
- Goal editor appearance and app selection list were inspected on the physical device. Two disabled temporary goals were saved and shown separately, then deleted. Notification permission was not requested; background threshold delivery, timezone changes, and reboot persistence remain unverified.
- The appearance picker, all three palettes, and follow-system restoration were inspected on the Android 13 physical device.
- On November 3, the current UI was installed on an L60 (Android 13, 360dp wide). The timer card and three single-row quick actions rendered without clipping. One-tap reading timing, pause, resume, stop, and the resulting local record were verified; the test record was then deleted. A separate existing local record remained visible. The device reported usage access as allowed. Today's app foreground total exceeded the independently reported screen-interactive time enough to fail the reader's quality gate, so the app correctly hid that total and now explains why. Live total accuracy and reminder delivery remain unverified by this check.
- A second 360dp visual pass refined the Today timer, top bar, navigation, and Trends hierarchy. The timer remains one tap from the Today card or bottom action. Sunset and morning themes were inspected on the device; a manual history under one minute uses compact seven-day marks and exact seconds instead of an almost empty full-height chart. This was a visual and layout check, not a new validation of device usage totals.
- `dart format .`, `flutter analyze`, `flutter test` (20 tests), and `flutter build apk --debug` passed. Android installs now use a stable debug key and `adb install -r` through `make run-android`; this command fails on a signature mismatch rather than automatically uninstalling an app containing local records.

## Outstanding work before a cross-platform release

1. Install full Xcode, connect an iPhone and validate the independent journal, SQLite/file picker, lifecycle, accessibility and production archive. For the separate device-usage module, obtain the Family Controls capability/distribution entitlement and implement/test protected reports, app selection and threshold monitoring. Apple's [Family Controls entitlement guide](https://developer.apple.com/documentation/familycontrols/requesting-the-family-controls-entitlement) describes the distribution request for the app and Screen Time API extensions.
2. Validate Android daily/app totals against the system's usage report on multiple devices. Test a saved goal across backgrounding, permission revocation, midnight and reboot. Android [JobScheduler](https://developer.android.com/reference/android/app/job/JobScheduler) scheduling is inexact; do not promise immediate delivery.
3. Validate P2 features with longer real-world use: multiple goals, weekday/weekend limits and the weekly review. The 30-day heatmap cannot fill dates for which the OS provides no trustworthy data.
4. Decide whether optional AI adds value after the non-AI product is validated. No protected iOS report data should be exported to Flutter or a cloud model. Apple's [Device Activity Report](https://developer.apple.com/documentation/deviceactivity/deviceactivityreport) runs in a protected extension.

The local debug APK is for review. Android release builds now require explicit production signing; a missing configuration fails instead of using a debug certificate. Actual signed bundle/IPA production acceptance remains pending. No store submission is requested.

## Durable journal milestone · 0.2.0 (2), November 5

- Decision: developer Elton; current product free; prepare both platforms without submitting to stores. Native journal records moved from preference JSON to transactional SQLite. Writes serialize and publish only after commit; malformed legacy data stays untouched. Android OS backup/transfer is disabled; export remains user-controlled.
- Physical L60 / Android 13 upgrade used the same debug certificate and `adb install -r`. `firstInstallTime` stayed November 3. Legacy and migrated rows matched exactly (1 existing record); SQLite integrity check returned `ok`. No real records were created or deleted during this migration check.
- JSON backup was saved through Android DocumentsUI to local Downloads. Restore preview showed the record count, then an identical merge preserved all SQLite rows and their count; a second integrity check returned `ok`. CSV opened the native save picker; Back cancelled and returned to Chronos. Automated tests cover CSV escaping, formula neutralization, snapshot pause accounting, duplicate imports, conflicts and overlapping restores. CSV file-save completion is not yet separately observed.
- Independent manual mode and its settings were inspected at 360dp. iOS routing has a widget check with a simulated iOS platform, 360-point width and 1.5x text; this is not an iOS native test. Its screen-time bridge remains unimplemented.
- Settings include backup scope, unencrypted-file disclosure, help, privacy, actual package version, Elton/free identity and open-source notices. The project Issues support URL is enabled. `docs/release/privacy.html` is a local policy draft; a public hosted URL and private support channel remain distribution preparation.
- `dart format .`, `flutter analyze --no-pub`, 31 Flutter tests, debug APK and Web builds passed during this milestone. `flutter build appbundle --release --no-pub` intentionally failed without signing credentials, confirming the release guard. `make release-check` correctly reports pending gates and returns a failure status; it is not a passed release certification.
- Unverified: native iOS build/device behavior, Android system-report accuracy, actual background threshold notifications, production signing and profile/release performance. See [release readiness](release/READINESS.md) for the acceptance gates.

## Android reliability · 0.2.1 (3), November 5

- User priority changed to Android; iOS development deferred. No iOS platform code changed.
- On L60 Android 13, system daily buckets began at 11:52 rather than midnight and the screen-interactive aggregate had an open running interval. These were insufficient for the previous quality gate. The reader now prefers covered foreground event intervals and only accepts aggregate fallback with exact natural-day bounds. This fixes a concrete source/boundary issue; it is not a certification against an independent system report.
- Pure Kotlin accounting handles cross-midnight clipping, lock/screen-off, pause/stop, duplicate resumes, old-activity events, shutdown/startup, clock rollback and unresolved conflicts across day boundaries. A physical observation exposed resume-before-unlock ordering; a dedicated regression test now checks counting from unlock. Source changes suppress cross-source comparisons.
- Goal checks share one serialized path, preserve malformed goal data, record explicit outcomes, respect channel blocks and revalidate goal configuration/date. Startup/upgrade/system receivers recover scheduling; cancellation stops obsolete work. Notification routes support real goals from manual/demo mode while retaining the saved mode preference. Android API 24–25 paths avoid API 26 channel/category calls, but older devices have not been physically tested.
- User explicitly enabled notifications. Through the actual UI, one temporary goal selected only Chronos with a 30-minute upper limit; its real usage exceeded that limit. A Chronos notification appeared in Android's notification list and shade. Repeated `cmd jobscheduler run -f` executions produced `already_notified`; notification creation/update timestamps and the full notification record stayed unchanged. Tapping the actual notification returned to the goals page, which showed the dedupe result.
- The temporary goal was deleted through its own confirmation dialog. SQLite rows matched the pre-update private backup exactly, integrity was `ok`, goals were unchanged and no new check markers remained. The separate test APK was removed; the main app was only replaced with `adb install -r`. No real hand-entered records were added or deleted.
- AndroidX instrumentation could not start on this device: the process remained `<pre-initialized>` on both ordinary and storage-compatibility attempts. Both were stopped without clearing data. The optional runner APK compiled, but there is no passing instrumentation result. The actual app/system checks above are the device evidence.
- `dart format .`, `flutter analyze --no-pub`, 33 Flutter tests, 12 native JUnit tests, debug APK and optional instrumentation APK builds passed locally. New Make targets cover native tests and Android-only readiness; CI also compiles Android and runs native tests. Native unit fixtures contain synthetic app IDs, never device history.
- Still pending: second-device/OEM and independent report comparison, natural periodic delay, midnight/time-zone/reboot acceptance, low-storage/process-death behavior, profile/release performance and production signing. The Android readiness report intentionally remains pending. iOS is outside the current iteration.
